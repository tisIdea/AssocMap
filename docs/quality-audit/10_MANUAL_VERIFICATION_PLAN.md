## How to prove F-005 instead of merely repeating clicks

Use two independent sessions logged in as the **same currently assigned Field Officer**: associations have one primary reviewer, so a different unassigned officer is an authorization test, not a valid competing reviewer. Use multiple server workers and confirm request/transaction overlap. Two tabs on a serial single-worker server prove repeated/stale handling, not row-lock blocking. Run approve/approve, approve/reject and reject/reject with valid rejection reasons on fresh eligible pending sandbox applications.

The first successful transaction determines the result. Confirm the waiting loser returns the controlled stale error, no terminal status is overwritten, and exactly one member exists only for approved outcomes. With Accept: application/json verify 409; HTML form requests use an error redirect rather than an HTTP409 page. Controller validation may reject an invalid reason before a status conflict; that is not a successful second decision.

For rollback, an operator-approved controlled harness/debugger should inject a failure **after** member/classification writes but before application completion; inspect all affected tables from an authorized test process. A failure before any insert or merely a successful single approval does not prove multi-write rollback. Higher isolation/lock-timeout behavior must be recorded separately; the patch retains existing DB exception handling. Relevant source: web/app/Services/MemberApplicationService.php::{approve,reject} and the reviewer/source-application constraints in SQL 001.

MEM-03 tests a separate association-wide President invariant across **different** IDs. Do not combine its result with the same-application F-005 claim.
