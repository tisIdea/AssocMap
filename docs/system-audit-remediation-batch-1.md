## Existing workflow effects

Projects with linked training or activity history can no longer change association, including when the link is archived. They can still receive otherwise-authorized edits within their current association. Unlinked projects retain the existing transfer permissions and destination/lifecycle checks. A GIS link alone does not introduce a transfer prohibition; its native preservation scenarios remain unexecuted. No history is automatically reassigned or deleted.

The existing transaction, actor/session-cutoff check, stable association locking, project lock, finalized-project rules and resource synchronization remain in place. Same-association updates return from the new guard without extra relationship queries. Transfers add bounded existence checks for the two relationship tables. This application guard does not add a reverse database constraint against arbitrary privileged SQL writes.

Malformed non-string text now fails validation instead of being coerced. Valid HTTP submissions retain string trimming, required fields and nullable optional fields. Public API schemas, Flutter code, routes, model names, database objects, other workspace labels and audit semantics are unchanged.

Setup no longer produces a ready database or APP_KEY automatically. Operators of fresh installations must perform the documented explicit steps; configured environments retain their existing key and database state.

## Deferred dependencies and recommended tests

These are source findings and proposed verification boundaries, not fixes or deployed exploit demonstrations.

- **F02 — transactional session freshness:** `ProgramActorService::lock()` compares the current profile cutoff with the request-loaded profile after locking role/profile; project writes already use it. `ProjectClosureService::finalize()` rechecks eligibility/role but does not compare that cutoff. Preserve the project-write guard used by this batch. A separate change should first reproduce stale-request behavior for cutoff changes, revocation, role changes and reassignment across remaining mutations, including denial without business/audit writes.
- **F03 — recovery invalidation:** `PasswordRecoveryController::updatePassword()` changes the provider password and regenerates the current local recovery session. It neither invokes the existing provider `signOutEverywhere()` helper nor advances the application's profile cutoff. Provider-side invalidation behavior is unverified; local session regeneration does not prove invalidation of other browser/mobile sessions. Test old access/refresh sessions, retained Laravel sessions, concurrent writes, uncertain password responses and logout failures before choosing a coordinated recovery/cutoff fix. No authentication/session code was changed here.
- **F04 — finalization lock order:** `ProgramActorService` obtains role then profile; `ProjectClosureService` obtains profile then role; Administrator revocation locks role before profiles. This confirms an ordering discrepancy with deadlock potential, not an executed deadlock. The new transfer guard introduces no new lock class or order. Separately exercise finalization versus revocation, cutoff changes, transfers and linked writes on disposable PostgreSQL, in both commit orders, before aligning the finalization path.
- **F08 — migration tracks:** Laravel's initial migrations create framework tables, while core AssocMap schema/history resides in canonical Supabase SQL. Later wrappers, including media 023 and GIS classification 024, execute referenced SQL files. Removing automatic migration from setup prevents an unreviewed execution path but does not reconcile the tracks. Inventory the actual approved target schema, owners/extensions/grants and ledger, design one installation/deployment sequence, then test it on a newly authorized disposable PostgreSQL/PostGIS target. Do not rewrite applied migration history or apply wrapper SQL twice.

Before release, run the 12 new native transfer scenarios in the guarded disposable harness under separate provisioning/migration authorization. Add real two-connection races for linking training/activity versus transferring a project in both commit orders, with cross-association denial, rollback and unchanged audit/GIS/history assertions. Check the deployed transfer error, malformed JSON/form inputs, valid submissions and Administrator label with authenticated role-specific browser sessions. Exercise setup on fresh/existing synthetic directories only in a later authorized bootstrap test.
